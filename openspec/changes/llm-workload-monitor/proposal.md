## Why

Edge devices running Open Horizon workloads often experience errors that go undetected until they cause service disruptions. Manual log monitoring is impractical at scale, and traditional monitoring solutions lack the intelligence to understand context-specific errors and propose remediation. An LLM-based monitoring service can autonomously discover workloads, analyze logs for errors, and generate actionable remediation proposals, reducing mean time to resolution and improving edge reliability.

## What Changes

- **New multi-arch container service** (x86_64, arm64) that runs an LLM for intelligent workload monitoring
- **Automated workload discovery** via Open Horizon anax API to detect registered and running services
- **Permission-based monitoring** that checks service definitions for opt-in monitoring consent
- **Intelligent log analysis** that monitors specified log files for errors and anomalies
- **Automated remediation proposals** generated by LLM analysis of error patterns and context
- **Open Horizon service integration** with proper service definition, policies, and deployment configuration

## Capabilities

### New Capabilities
- `workload-discovery`: Periodic polling of Open Horizon anax API to discover registered and running workloads on the local node
- `log-monitoring`: Permission-based monitoring of workload log files as specified in service definitions
- `error-analysis`: LLM-powered analysis of log entries to identify errors, patterns, and root causes
- `remediation-proposals`: Generation of actionable remediation proposals based on error analysis and workload context

## Impact

**Affected Systems:**
- Open Horizon agent (anax API) - read-only queries for workload discovery
- Container runtime (Docker/Podman) - for running the LLM monitoring service
- Local filesystem - read access to workload log files (with permission)

**Dependencies:**
- Open Horizon agent running on the node
- LLM runtime (e.g., Ollama, llama.cpp) for inference
- Python runtime for service orchestration
- Access to anax API (typically http://localhost:8510)

**APIs:**
- Anax API endpoints: `/node`, `/service/config`, `/agreement`
- Service definition schema extension for monitoring permissions

**Breaking Changes:**
None - this is a new optional service that workloads can opt into
