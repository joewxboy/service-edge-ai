# Service developer guide

**Audience:** you own an Open Horizon service and want the edge-ai monitor to
watch its logs and propose fixes when it errors. You do not need to know how the
monitor works internally.

Everything here has been verified against a live Open Horizon hub and edge node.

---

## What you get

When your workload logs an error, a JSON proposal appears on the node. This is a
real one, produced by the monitor from a sample workload:

```json
{
  "error_summary": "Failed to connect to database due to a refused connection",
  "root_cause": "Database port is not open or not reachable",
  "severity": "high",
  "remediation_steps": [
    "Step 1: Check the database server status and ensure it's running and listening on port 5432",
    "Step 2: Verify firewall rules allow incoming connections to the database server",
    "Step 3: Consider increasing the timeout value for the database connection attempt if necessary",
    "Step 4: Verify myorg/sample-monitored-workload v1.0.0 recovered by re-checking /var/log/workloads/sample/app.log for further occurrences."
  ],
  "confidence": 0.8,
  "requires_human_review": true,
  "disclaimer": "This remediation proposal is generated by an AI system. Validate all steps before execution in production environments.",
  "metadata": {
    "timestamp": "2026-08-14T12:59:54.692694+00:00",
    "detected_at": "2026-08-14T12:59:53.691375+00:00",
    "workload_id": "myorg/sample-monitored-workload_1.0.0_amd64",
    "service_name": "sample-monitored-workload",
    "service_version": "1.0.0",
    "organization": "myorg",
    "log_path": "/var/log/workloads/sample/app.log",
    "line_number": 4,
    "matched_pattern": "ERROR",
    "occurrences": 1,
    "analysis_duration_ms": 37457
  }
}
```

That workload logs `ERROR could not connect to database at db:5432: connection
refused` on a timer; everything above was inferred from that line and its
surrounding context by a 3B model running on the node.

Proposals are **advisory only**. The monitor never restarts, reconfigures, or
otherwise touches your workload — it reads logs and writes JSON.

### What this costs you

| | |
|---|---|
| Changes to your code | none |
| Changes to your service definition | 2–4 environment variables + a log bind |
| Runtime overhead in your container | none — a separate service does the work |
| Data leaving the node | none — inference is local |

## Before you start

Ask whoever operates the edge node to confirm three things. Without them your
opt-in is valid but nothing will happen.

1. **The monitor is deployed on the node.**
   ```shell
   hzn agreement list | grep service-edge-ai
   ```
2. **The node advertises `monitoring: true`** — the monitor's deployment policy
   requires it.
   ```shell
   hzn policy list | grep -A2 '"monitoring"'
   ```
3. **The shared log directory exists**, if you use the host-path approach below.
   ```shell
   ls -ld /var/log/workloads
   ```

The monitor's health endpoint answers all three at once:

```shell
curl -sS http://127.0.0.1:8080/health | jq
```

## Step 1 — Write logs where the monitor can read them

The monitor reads **files**, not container stdout, and it resolves paths inside
**its own** container. So your workload and the monitor must share a volume.

Pick one of the two patterns below.

### Pattern A: shared host directory (what the monitor ships with)

Your workload binds a subdirectory of `/var/log/workloads` read-write:

```json
"deployment": {
  "services": {
    "sensor": {
      "image": "examples/sensor:1.2.0",
      "privileged": true,
      "binds": ["/var/log/workloads/sensor:/var/log/app:rw"]
    }
  }
}
```

Your code writes to `/var/log/app/app.log`. The monitor sees the same file at
`/var/log/workloads/sensor/app.log` — that second path is what goes in
`MONITORING_LOG_PATHS`.

> ⚠️ **`privileged: true` is required here.** `/var/log/workloads` is
> root-owned, and Open Horizon refuses a writable bind to a root-owned host
> directory from an unprivileged workload:
>
> ```
> Deployment config ... contains unsupported bind for a workload,
> Write permission for bind to /var/log/workloads/sensor is denied
> ```
>
> The workload then crash-loops. The node must also advertise
> `openhorizon.allowPrivileged: true`, or no agreement will form at all.

Nothing else needs changing: the monitor already mounts the whole tree read-only.

### Pattern B: shared named volume (no privilege needed)

If you cannot or will not run privileged, use a named volume — Open Horizon
accepts `:rw` on those without privilege:

```json
"binds": ["edge-ai-workload-logs:/var/log/app:rw"]
```

**This requires a matching change on the monitor side**, which you do not own:
the monitor's service definition must mount the same named volume, e.g.
`edge-ai-workload-logs:/var/log/workloads:ro`. Coordinate with the node operator
before choosing this pattern, and agree on the volume name and the directory
layout inside it.

### If your workload only logs to stdout

Configure your logging library to *also* write a file into the shared mount.
That is strongly preferred over pointing the monitor at Docker's json-file log,
because container IDs change on every restart:

```
# fragile — the id changes whenever the container is recreated
MONITORING_LOG_PATHS=/var/lib/docker/containers/<id>/<id>-json.log
```

## Step 2 — Declare the opt-in

Add the `MONITORING_*` environment variables **inside the deployment section**:

```json
"deployment": {
  "services": {
    "sensor": {
      "image": "examples/sensor:1.2.0",
      "privileged": true,
      "binds": ["/var/log/workloads/sensor:/var/log/app:rw"],
      "environment": [
        "MONITORING_ENABLED=true",
        "MONITORING_LOG_PATHS=/var/log/workloads/sensor/app.log",
        "MONITORING_ERROR_PATTERNS=ERROR,FATAL,SensorFault"
      ]
    }
  }
}
```

> ⚠️ **They must be inside `deployment`, not at the top level of the service
> definition.** The Open Horizon exchange stores only its known service schema
> fields and silently discards anything else, so a top-level `monitoring`
> section would be dropped at publish time and never reach the node. The
> `deployment` string is stored verbatim and signed, so variables declared there
> arrive intact.

| Variable | Required | Default | Meaning |
|---|---|---|---|
| `MONITORING_ENABLED` | yes | *(absent = off)* | `true`, `1`, or `yes`, case-insensitive. Anything else means off. |
| `MONITORING_LOG_PATHS` | yes when enabled | — | Files to tail, **as the monitor sees them**. |
| `MONITORING_ERROR_PATTERNS` | no | `ERROR,FATAL,Exception,CRITICAL` | Case-insensitive patterns marking a line as an error. |
| `MONITORING_CONTEXT_PATHS` | no | — | Docs to steer the model (SKILL.md, runbooks) |
| `MONITORING_EXPORT` | no | `false` | Consent to your log-derived content leaving the node if the operator has configured [export](northbound-export.md). Without it, only counts and identity are exported. |

**`MONITORING_CONTEXT_PATHS` is the highest-leverage thing you can add.** Given
a runbook, the model names your actual components and returns your actual
recovery commands instead of generic advice — see
[context-and-steering.md](context-and-steering.md) for a measured before/after.

The list variables are comma-separated. If a value starts with `[` it is parsed
as a JSON array instead — which is how you write a pattern containing a comma:

```
MONITORING_ERROR_PATTERNS=["retry a{1,3} failed", "FATAL"]
```

A malformed value disables monitoring for your workload and logs a warning,
rather than monitoring with half a configuration.

own service:

```shell
export HZN_ORG_ID=<your-org>

hzn exchange service publish -O -I \
  --json-file=docs/examples/service.definition.verified-sample.json
```

It still needs a deployment policy to be scheduled — see step 3.

## Step 3 — Publish and deploy

**1. Publish the service.**

```shell
hzn exchange service publish -O -P --json-file=service.definition.json
```

`-P` pins the image to its sha256 digest, which requires the image to already be
in a registry the node can pull from. While iterating locally, `-I` keeps the
plain tag instead.

**2. Publish a deployment policy**, unless one already schedules your service.
Publishing alone puts the definition in the exchange; it does not deploy
anything.

```json
{
  "label": "my-service",
  "description": "Deploys my service to monitored nodes.",
  "service": {
    "name": "example.com.sensor",
    "org": "examples",
    "arch": "amd64",
    "serviceVersions": [{ "version": "1.2.0" }]
  },
  "properties": [],
  "constraints": ["monitoring == true"]
}
```

```shell
hzn exchange deployment addpolicy -f deployment.policy.json \
  examples/policy-example.com.sensor
```

The `monitoring == true` constraint is optional — it simply confines the
workload to nodes that run the monitor. Use whatever constraints your service
actually needs.

**3. Confirm compatibility before waiting on an agreement.**

```shell
hzn deploycheck all -t device -b examples/policy-example.com.sensor
```

This reports exactly which property or constraint blocks deployment, which is
much faster than watching `hzn agreement list` and guessing.

> ⚠️ **Republishing the same version does not redeploy a running workload.** The
> agent keeps the existing agreement and your new variables never take effect.
> Either bump the version, or force re-negotiation:
>
> ```shell
> hzn agreement list          # find your agreement id
> hzn agreement cancel <id>   # agent re-negotiates within ~1 minute
> ```

## Step 4 — Verify it worked

Work down this list; each step tells you exactly where a break is.

**1. Did the variables reach the node?**

```shell
curl -sS http://localhost:8510/service \
  | jq -r '.definitions.active[] | select(.specRef=="example.com.sensor") | .deployment' \
  | jq '.services[].environment'
```

Expect your three variables. `null` means they never arrived — they are almost
certainly at the top level of your service definition instead of inside
`deployment`.

**2. Is your workload running and writing?**

```shell
hzn agreement list | grep sensor
tail -f /var/log/workloads/sensor/app.log
```

**3. Does the monitor see you?**

```shell
curl -sS http://127.0.0.1:8080/health | jq
```

```json
{
  "workloads_discovered": 3,
  "workloads_monitored": 1,
  "log_paths_watched": 1
}
```

`workloads_monitored: 0` means the opt-in did not take — go back to step 1.
`log_paths_watched: 0` means the path is not readable from the monitor's
container; check the bind.

**4. Trigger an error and wait.**

```shell
echo "$(date -Iseconds) ERROR test failure for monitoring validation" \
  | sudo tee -a /var/log/workloads/sensor/app.log
```

Analysis takes **under a minute to a few minutes** depending on the node's CPU
and model — around 55 s on an 8-core x86_64 node with the default 3B model.
Watch the counters move:

```shell
watch -n5 'curl -sS http://127.0.0.1:8080/health | jq "{analyses_completed, analyses_failed, proposals_written}"'
```

**5. Read the proposal.**

```shell
docker run --rm -v edge-ai-monitor-state:/state busybox \
  find /state/proposals -name '*.json'

docker run --rm -v edge-ai-monitor-state:/state busybox \
  cat /state/proposals/<workload>/<problem-key>.json
```

Proposals are written to
`/var/lib/monitor/proposals/<workload>/<problem-key>.json` — **one file per
distinct problem**, not per occurrence. A recurring error updates the same file,
accumulating `total_occurrences` and advancing `last_seen`.

## Writing good error patterns

Each entry is a **case-insensitive regular expression**. An entry that is not a
valid regex falls back to a literal substring match, so `error(` works as
written rather than blowing up.

**Be specific.** Every match costs an LLM analysis, and inference is the
bottleneck — roughly one analysis per minute on a CPU-only node. A pattern
matching every `INFO` line will fill the 50-request queue, at which point the
monitor sheds the lowest-severity work.

| Instead of | Prefer | Why |
|---|---|---|
| `error` | `ERROR\|FATAL` | `error` also matches "no errors found" |
| `.*fail.*` | `failed to (connect\|authenticate)` | Bounded to real failure modes |
| `warn` | *(omit)* | Warnings are usually noise; let the defaults handle real errors |

**Domain patterns are where this pays off.** The monitor knows nothing about
your service, so patterns naming your own failure modes — `SensorFault`,
`upstream timed out`, `HTTP 5[0-9]{2}` — produce far more useful analyses than
generic severity keywords.

### What happens to repeated errors

The same error 3+ times within 5 minutes becomes **one** analysis carrying an
occurrence count, not three. Signatures normalise digits, so `retry 1 of 5` and
`retry 2 of 5` count as the same error. A completed analysis is reused for 15
minutes, so a flapping workload does not re-run inference for an error already
explained.

This is worth knowing when testing: firing the same test line twice usually
produces one proposal, not two.

## Reading a proposal

| Field | What to do with it |
|---|---|
| `error_summary` | One-line description of what went wrong |
| `root_cause` | The model's best explanation — verify before acting |
| `severity` | `low`, `medium`, `high`, or `critical` |
| `remediation_steps` | Ordered actions. The final step is always a verification step |
| `confidence` | `0.0`–`1.0`. Below `0.5` the proposal also carries diagnostic steps |
| `requires_human_review` | `false` **only** when severity is `low`/`medium` *and* confidence ≥ `0.8`. `true` in every other case, including high severity at high confidence |
| `metadata.occurrences` | How many times this error fired in the window |
| `metadata.line_number` | Where in the log file the error was found |

**Treat every proposal as a hypothesis, not an instruction.** They are generated
by a small quantized model from a 100-line window of your logs. `confidence` and
`requires_human_review` are there to tell you how much weight to give it.

## Turning monitoring off

Set `MONITORING_ENABLED=false`, or remove the variables entirely, and republish
(remembering the re-negotiation caveat in step 3). The monitor stops watching
your logs on its next discovery poll, within 60 seconds by default.

Your workload keeps running normally with the monitor absent, gone, or broken —
nothing about your service depends on it.

## Common mistakes

| Symptom | Cause |
|---|---|
| Variables missing from `/service` output | Declared at the top level instead of inside `deployment` |
| Workload crash-loops, "Write permission for bind ... denied" | Writable bind to a root-owned host dir without `privileged: true` |
| No agreement forms at all | Node lacks `openhorizon.allowPrivileged: true` (needed for privileged workloads) or `monitoring: true` |
| `workloads_monitored: 0` | `MONITORING_ENABLED` absent, workload not running, or no log paths declared |
| `log_paths_watched: 0` | Path is correct for your container, not the monitor's |
| Republished, nothing changed | Same version — cancel the agreement to force re-negotiation |
| `analyses_failed` climbing with timeouts | Node's `MONITOR_LLM_TIMEOUT` too low for its CPU; an operator setting, not yours |
| One proposal for several identical errors | Working as designed — errors aggregate |
