# service-edge-ai
![Architecture](https://img.shields.io/badge/architecture-arm64%2C%20x86-green)
![License](https://img.shields.io/github/license/open-horizon-services/service-edge-ai)
![Contributors](https://img.shields.io/github/contributors/open-horizon-services/service-edge-ai)

An Open Horizon service that monitors other edge workloads with a **local LLM**.
It discovers what is running on the node through the anax API, tails the logs of
workloads that have opted in, and turns detected errors into structured
remediation proposals — all on-device, with no cloud connectivity required.

```
workload logs ──▶ error detected ──▶ local LLM analysis ──▶ remediation proposal JSON
```

Monitoring is **opt-in**. A workload is never read unless its service definition
explicitly asks for it.

## How it works

1. **Discovery** — polls the anax API every 60 seconds for registered and
   running workloads.
2. **Permission check** — only workloads whose service definition sets
   `MONITORING_ENABLED=true` are eligible.
3. **Log monitoring** — tails the declared log paths, matching error patterns
   case-insensitively and collecting 50 lines of context either side.
4. **Analysis** — sends the error, workload metadata, and any operator-supplied
   documentation (SKILL.md files, runbooks) to a local Ollama model, which
   returns a structured JSON verdict with a severity and confidence score.
5. **Proposal** — writes an actionable proposal to
   `/var/lib/monitor/proposals/<workload>/<timestamp>.json`.

See [docs/architecture.md](docs/architecture.md) for the component and data-flow
diagrams.

### Example proposal

```json
{
  "error_summary": "The sensor service is unable to connect to the database.",
  "root_cause": "The database server at db.internal:5432 is not reachable or is down.",
  "severity": "critical",
  "remediation_steps": [
    "Step 1: Verify that the database server is running and accessible from the sensor's network.",
    "Step 2: Check the network configuration for firewall rules blocking port 5432 on db.internal.",
    "Step 3: Review the database server logs for errors explaining why it cannot accept connections.",
    "Step 4: Verify examples/sensor v1.2.0 recovered by re-checking /var/log/workloads/sensor/app.log."
  ],
  "confidence": 0.95,
  "requires_human_review": true,
  "disclaimer": "This remediation proposal is generated by an AI system. Validate all steps before execution in production environments.",
  "metadata": {
    "timestamp": "2026-08-13T19:42:09.429591+00:00",
    "workload_id": "examples/example.com.sensor_1.2.0_amd64",
    "service_name": "sensor",
    "log_path": "/var/log/workloads/sensor/app.log",
    "line_number": 6,
    "occurrences": 3,
    "analysis_duration_ms": 136014
  }
}
```

Proposals are **advisory**. The service never executes remediation itself.

## Prerequisites

**Management Hub:** [Install the Open Horizon Management Hub](https://open-horizon.github.io/quick-start)
or use an existing hub. You may [apply for a temporary account](https://wiki.lfedge.org/display/LE/Open+Horizon+Management+Hub+Developer+Instance)
on the community hub.

**Edge node:** An x86_64 or arm64 Linux machine with the Open Horizon agent
(anax) installed and registered, and **at least 4 GB of RAM** — local inference
with a 3B quantized model needs roughly 2 GB beyond the runtime.

**Optional utilities:** `make`, `git`, `jq`, `curl`, `docker`.

Confirm the agent is present and talking to a hub:

```shell
hzn version
hzn node list | jq '.configstate.state'
```

## Quick start

### Locally, without a hub

`docker-compose.yml` starts the monitor next to a sample workload that emits
errors on a timer:

```shell
docker compose up --build
curl -sS http://127.0.0.1:8080/health | jq
```

### On an Open Horizon node

```shell
export HZN_ORG_ID=<your-org>
sudo mkdir -p /var/log/workloads     # shared log mount

make publish
```

Full instructions: [docs/deployment.md](docs/deployment.md).

## Opting a workload in

Add `MONITORING_*` environment variables to the **deployment** section of the
workload's service definition:

```json
{
  "deployment": {
    "services": {
      "sensor": {
        "image": "examples/sensor:1.2.0",
        "environment": [
          "MONITORING_ENABLED=true",
          "MONITORING_LOG_PATHS=/var/log/workloads/sensor/app.log",
          "MONITORING_ERROR_PATTERNS=ERROR,FATAL,SensorFault"
        ]
      }
    }
  }
}
```

They must live inside `deployment` — the Open Horizon exchange discards unknown
top-level service definition fields, so a custom `monitoring` section would never
reach the node.

`MONITORING_LOG_PATHS` is resolved **inside the monitor container**, so the
workload and the monitor must share a volume — and a writable bind to the
root-owned `/var/log/workloads` additionally needs `privileged: true`.

**→ Full walkthrough: [docs/service-developer-guide.md](docs/service-developer-guide.md)**
— sharing logs, publishing, verifying, and reading proposals, with runnable
[examples](docs/examples/).

Omitting the variables, or setting `MONITORING_ENABLED=false`, means the workload
is discovered but never read.

## Configuration

Settings come from `config/config.yaml`, overridden by environment variables
(which is how Open Horizon `userInput` supplies them). **Full reference with
tuning guidance: [docs/tuning.md](docs/tuning.md).**

| Variable | Default | Meaning |
|---|---|---|
| `MONITOR_ANAX_URL` | `http://localhost:8510` | Open Horizon agent API |
| `MONITOR_POLL_INTERVAL` | `60` | Seconds between discovery polls |
| `MONITOR_LOG_POLL_INTERVAL` | `1` | Seconds between log reads |
| `MONITOR_MAX_BUFFER_MB` | `100` | In-memory log buffer ceiling |
| `MONITOR_LLM_MODEL` | `llama3.2:3b-instruct-q4_K_M` | Ollama model |
| `MONITOR_LLM_HOST` | `http://localhost:11434` | Ollama runtime |
| `MONITOR_LLM_TIMEOUT` | `30` | Seconds before an analysis is cancelled |
| `MONITOR_LLM_AUTO_PULL` | `true` | Pull the model if missing |
| `MONITOR_MAX_QUEUE_SIZE` | `50` | Pending analyses before shedding |
| `MONITOR_CACHE_TTL` | `900` | Seconds an analysis is reused |
| `MONITOR_CONTEXT_DIR` | `/etc/edge-ai-monitor/context` | Node-wide knowledge injected into prompts |
| `MONITOR_CONTEXT_ENABLED` | `true` | Master switch for knowledge injection |
| `MONITOR_CONTEXT_MAX_BYTES` | `8000` | Guidance budget per prompt |
| `MONITOR_PROPOSAL_DIR` | `/var/lib/monitor/proposals` | Proposal output |
| `MONITOR_LOG_LEVEL` | `INFO` | Logging verbosity |
| `MONITOR_HEALTH_PORT` | `8080` | Health endpoint port |

Validate configuration and dependencies without starting the service:

```shell
edge-ai-monitor --check
```

```json
  "healthy": true,
  "startup_errors": [],
  "workloads_discovered": 3,
  "workloads_monitored": 1,
  "log_paths_watched": 2,
  "analysis_queue_depth": 0,

  "analyses_failed": 0,
  "analyses_dropped": 0,
  "proposals_written": 4,
  "proposal_storage_failures": 0
}
```

Returns 200 when running, 503 while shutting down. A temporarily unreachable
dependency appears in `startup_errors` without making the service unhealthy —
the loops recover on their own.

## Privacy and resource guarantees

- **Opt-in only.** No `MONITORING_ENABLED=true` means no log access, ever.
- **Local inference.** Log content never leaves the node.
- **Read-only.** Logs are mounted read-only; the anax API is only ever queried.
- **No persistence beyond proposals.** Log content is buffered in memory and
  discarded.
- **Bounded.** 100 MB log buffer, 50-request analysis queue, 4 GB container
  memory limit — all enforced, with defined shedding behaviour at each limit.

## Development

```shell
pip install -e '.[dev]'
make unittest
```

The suite is hermetic: anax HTTP and the Ollama runtime are stubbed, and log
tests drive real files in a temp directory. Sample logs and API fixtures live in
`tests/fixtures/`.
